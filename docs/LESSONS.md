# 실수 기록 (LESSONS)

이 저장소에서 실제로 생긴 문제를 모두 적는다. 새 문제가 생기면 같은 형식으로 **해당 절 맨 아래에 추가**하고, 재발 방지 테스트나 규칙을 반드시 함께 남긴다. 요약 규칙은 [CLAUDE.md](../CLAUDE.md)에 있다. 짝 도구 [music-folder-organizer](https://github.com/microhan1/music-folder-organizer)에도 같은 형식의 `docs/LESSONS.md`가 있다.

형식: 증상 → 원인 → 해결 → 재발 방지. 2026-10-01 이전 항목은 커밋 기록에서 옮겨 적었다(괄호 안은 커밋).

## A. 제품 코드 버그

### A1. 자동 선택이 이미 있는 태그를 덮어씀 (`57d8ba0`)
- 증상: 태그가 다 있는 베스트 앨범 rip에 일괄 처리를 돌리면 앨범·연도·표지가 원곡의 원래 앨범 것으로 바뀜
- 원인: 자동 선택(일괄, CLI `--auto`)이 직접 고른 것과 똑같이 모든 칸을 덮어씀
- 해결: 자동 선택은 빈 칸만 채움. 사용자가 직접 「선택 적용」하거나 `--overwrite`일 때만 바꿈
- 재발 방지: `test_apply_candidate_fill_gaps_vs_overwrite`. 규칙: **사람이 확인하지 않는 일괄 동작은 있는 값을 지우지 않는다**

### A2. 한 글자 일본어 제목이 "무의미한 이름"으로 잡혀 자동 선택이 막힘 (`57d8ba0`)
- 증상: `唱`, `虹` 등 17곡이 자동 선택에서 빠짐
- 원인: 짧은 제목을 무의미한 파일명(`track01` 류)과 같이 취급
- 해결: 숫자·track 류만 무의미한 이름으로 봄
- 재발 방지: `test_generic_names`. 규칙: 길이로 판단하지 말고 패턴으로 판단한다(CJK 제목은 짧다)

### A3. 파일명의 버전 표기를 가수-제목 구분으로 잘라 엉뚱한 곡이 1위 (`326268f`)
- 증상: `Time Pavement - Karaoke.flac` → 가수 Time Pavement, 제목 Karaoke (52점 오답)
- 해결: 뒤에 붙은 말이 Karaoke·off vocal·TV size 등 버전 표기면 제목의 일부로 봄. karaoke·off vocal·instrumental은 같은 말로 비교
- 재발 방지: `test_version_suffix_is_part_of_the_title`, `test_karaoke_and_off_vocal_compare_equal`, `test_base_title_drops_version_suffix_only`

### A4. 소리로 찾기와 텍스트 검색의 앨범명이 다름 (`b64478f`)
- 원인: AcoustID 발매 목록은 순서가 의미 없고 번역판 pseudo-release가 섞임
- 해결: 상위 3개 후보는 MusicBrainz 녹음 조회로 가장 이른 정식 발매 정보를 다시 읽음
- 재발 방지: `test_mb_parsing_prefers_official_album`. 규칙: 외부 API 목록의 "첫 번째"를 정답으로 믿지 않는다

### A5. 표지가 없는 후보가 많음 (`52f340c`)
- 원인: Cover Art Archive에는 발매·발매 그룹 모두 표지가 없는 경우가 많음(HTTP 500 포함)
- 해결: 발매 그룹 표지 → iTunes 앨범 검색(이름 유사도 0.6 이상) 순으로 폴백
- 재발 방지: `test_itunes_album_artwork_picks_matching_album`, `test_mb_parsing_keeps_release_group_id`

### A6. 창 모드 exe에서 소리로 찾기가 실패할 수 있음 (`1abc728`)
- 원인: 콘솔 없는 exe는 자식 프로세스(fpcalc)에 물려줄 표준 입력 핸들이 없음
- 해결: `stdin=DEVNULL` 명시, "fpcalc 없음"과 "실행 실패"를 구분, 원인을 exe 옆 `music-tag-filler.log`에 기록
- 재발 방지: 자동 테스트 없음 → 규칙: **외부 프로그램을 부르는 기능은 콘솔 없는 exe로 직접 확인한다**

### A7. 검색이 파일당 4.7~7.6초 (`a68f1a5`)
- 원인: 응답 시간이 아니라 요청 간격 대기. 한국어 기본값 KR 스토어는 음원이 없어 빈 결과 뒤 3.1초 대기 후 US 폴백
- 해결: 빈 스토어 건너뛰기, iTunes는 "60초 창에 20회" 제한, iTunes·MusicBrainz 동시 호출, 썸네일 병렬 → 파일당 0.3~2.1초
- 재발 방지: `test_window_allows_burst_then_paces`, `test_empty_storefront_is_skipped` 등 `tests/test_net.py`. 규칙: 느리면 먼저 **어디서 기다리는지 잰다**

### A8. 300곡을 넣으면 메모리 +240MB (`d85f015`)
- 원인: 목록의 모든 파일이 표지 원본 바이트를 들고 있음
- 해결: 태그만 유지하고 표지는 보일 때·저장할 때 다시 읽음, 내려받은 표지는 세션 임시 폴더에 → +2MB
- 재발 방지: 화면 하단 메모리 사용량 표시. 규칙: 파일마다 붙는 큰 데이터는 메모리에 쌓지 않는다

### A9. 파일 목록이 클릭·입력 때마다 튐 (`8204a32`)
- 원인: 갱신 때 모든 줄을 지우고 다시 넣음 → 스크롤·선택이 흔들림
- 해결: 바뀐 줄만 제자리에서 고치고 스크롤 위치 복원
- 재발 방지: 자동 테스트 없음 → 규칙: Treeview는 전체 다시 그리기보다 제자리 갱신. 40곡 끝까지 내린 상태에서 클릭·입력으로 확인

### A10. 후보 표 썸네일이 대부분 비어 있음 (`ad5b6fe`)
- 원인: 표를 다시 채울 때마다 진행 중이던 썸네일 요청을 전부 버림 → 23줄 중 2줄만 표시
- 해결: URL마다 한 번만 받아 캐시하는 영구 풀
- 재발 방지: 자동 테스트 없음 → 규칙: 비동기 작업을 화면 갱신과 같이 취소하지 않는다

### A11. 로딩 표시가 검색 후에도 남음 (`fab4d7e`)
- 원인: 마무리 블록에서 플래그만 끄고 위젯은 그대로 → `place_forget`이 불리지 않음

### A12. 서버에 보내는 앱 버전이 0.1.0에 머묾 (v0.1.7에서 고침, `ae548ea`)
- 증상: v0.1.1~v0.1.6 동안 MusicBrainz·iTunes·AcoustID에 `music-tag-filler/0.1.0`으로 요청
- 원인: `net.py`의 `APP_VERSION`을 릴리스 때 올리는 절차가 없었음. MusicBrainz는 정확한 앱 이름·버전을 요구
- 해결: 0.1.7로 맞추고 코드에 "릴리스마다 올린다" 주석
- 재발 방지: [CLAUDE.md](../CLAUDE.md)의 릴리스 점검 1번

### A13. 파일 이름을 바꿀 때 백업을 놓쳐 되돌리기가 안 될 수 있음 (심각)
- 증상: "저장할 때 파일 이름 바꾸기"를 켜고 저장할 때 백업(`.tagbak.json`)이 잠깐 열려 있으면(백신·검색 색인 등) 음악 파일만 `가수 - 제목.mp3`로 바뀌고 백업은 옛 이름에 남음. 화면은 "저장됨, 원래 정보는 `가수 - 제목.mp3.tagbak.json`에"라고 없는 파일을 안내하고, 되돌리기는 "백업 없음". 짝 도구(음악 폴더 정리)에서 같은 종류의 문제(로그 저장 실패를 삼킴)를 고친 뒤 이 저장소를 점검하다 재현함
- 원인: `rename_file`이 음악 파일을 먼저 옮기고 백업 옮기기 실패는 `except OSError: pass`로 삼킴. 함께 발견: ① 이미 있는 백업은 읽어 보지 않고 믿어서, 깨진 백업이 있으면 태그를 쓴 뒤 되돌리기가 실패 ② 태그를 쓴 뒤 이름 바꾸기가 실패하면 "읽기 전용이거나 사용 중"이라는 저장 실패로 보고(실제로는 저장됨) ③ `rename_target`이 같은 이름의 남은 백업을 확인하지 않아 그 백업을 덮어쓸 수 있음
- 해결: `rename_file`이 백업을 먼저 옮기고 음악 파일을 옮김. 음악 파일이 실패하면 백업을 되돌려 놓고 `RenameFailed`(백업이 실제로 있는 곳 포함). `save_file`은 이를 받아 `rename_failed`로 알림(GUI 경고 창, CLI 오류 출력) — 태그는 저장됐고 파일과 백업은 옛 이름 그대로. `make_backup`은 기존 백업을 읽어 보고 깨졌으면 `BrokenBackup`으로 아무것도 쓰지 않음. `rename_target`은 남은 백업이 있는 이름도 건너뜀
- 재발 방지: `tests/test_save_safety.py` 6개(백업이 열린 채 저장, 음악 파일이 열린 채 저장, 백업 되돌리기도 실패, 깨진 백업, 남은 백업 이름, 정상 이름 바꾸기). 모두 옛 코드에서 실패. 규칙: **되돌리기 수단(백업)과 바꾼 파일은 항상 짝으로 움직이고, 짝을 지키지 못하면 `pass`가 아니라 원래대로 돌려놓고 알린다**

### A14. 가사 서버(LRCLIB)의 503에 요청 간격을 영구히 늘려 곡당 36초 (2026-10-11, 가사 기능 검토 중)
- 증상: 라이브러리 가사 조회 시험에서 20곡에 719초
- 원인: `net.request`가 모든 503을 MusicBrainz의 요청 제한처럼 다뤄 `slow_down`으로 호스트 간격을 최대 10초까지 늘리고 줄이지 않음. LRCLIB의 503은 `ServerOverloaded`(Retry-After: 1)로, 요청 속도와 관계없이 17~47% 나옴(0.3초·1초 간격에서 같은 비율)
- 해결: `net.OVERLOAD_503_HOSTS`의 호스트는 503에 그 요청만 1·2·4초 기다려 다시 보내고 간격은 그대로 둠. 429는 그대로 요청 제한으로 처리. 가사 조회 실패는 저장을 막지 않고 "서버가 바빠 찾지 못함"으로 남김(연속 5번이면 그 저장에서는 가사 조회를 멈춤, 바빴던 곡은 끝에 한 번 더)
- 재발 방지: `test_lrclib_503_backs_off_without_slowing_the_host`, `test_musicbrainz_503_still_slows_the_host`. 규칙: **같은 상태 코드라도 서버마다 뜻이 다르다. 새 서버를 붙이면 문서의 오류 표부터 읽는다**

### A15. 규칙을 다 통과한 가사가 가짜 (2026-10-12, 가사 기능 개발 중)
- 증상: YOASOBI 「アイドル」에 원곡이 아닌 가사가 들어감. 테스트와 자동 확인(다시 읽기·되돌리기 SHA)은 모두 통과했고, 화면 시험에서 「가사 보기」 창을 열어 보고서야 발견
- 원인: LRCLIB는 누구나 올릴 수 있음. 같은 가짜 글이 번호가 이어진 6개 기록(길이만 다름)으로 올라와 아티스트·제목·버전·길이 규칙을 모두 통과했고, "타임스탬프 있고 길이가 가까운 것"을 고르는 규칙이 그중 하나를 고름. 또 두 검색 결과를 따로 판정해, 가짜만 담긴 첫 검색 결과로 결정됨(평가 스크립트는 두 결과를 합쳐 봐서 이 차이를 놓침)
- 해결: 거의 같은 글(유사도 0.95 이상)은 한 출처로 묶고, 서로 일치하는(0.6 이상) 출처끼리 모은 가장 큰 무리에서 고름. 같은 크기의 무리가 갈리면 넣지 않음(`CONFLICT`, 화면: "올라온 가사끼리 내용이 달라 넣지 않음"). 두 검색을 모두 받아 함께 판정하고, 하나라도 실패하면 BUSY. 가사가 이미 있던 25곡과의 대조 결과는 그대로(25/25), 표본 110곡 중 4곡이 "넣지 않음"으로 바뀜
- 재발 방지: `test_copies_of_one_wrong_text_do_not_outvote_a_real_one`, `test_two_real_sources_beat_many_copies`, `test_both_searches_are_judged_together`, `test_one_failed_search_means_try_later`. 규칙: **남이 올린 데이터는 메타데이터가 다 맞아도 내용이 틀릴 수 있다. 내용이 중요한 결과(가사·표지)는 직접 열어 확인하고, 평가 스크립트는 제품 코드와 같은 경로로 판정한다**

### A16. 가사 기능 예외 점검에서 나온 것 (2026-10-12, 출시 전)
- 증상(코드 검토와 고장 재현으로 찾음): ① 타임스탬프만 있는 기록은 글자를 빼면 빈 문자열인데 "찾음"으로 처리되어, 빈 가사를 쓰면 "가사 삭제"가 되면서 "넣음"으로 셈 ② `(Instrumental)`·`♪`만 있는 글, 3만 자가 넘는 글, 제어 문자·짝 없는 서로게이트(저장 실패)를 그대로 씀 ③ 이름 비교의 부분 일치 보정 때문에 "AI"와 "Aimer", "Song"과 "Song 2"가 통과할 수 있음 ④ 「インスト」「TVサイズ」「반주」「伴奏」 같은 비영어 버전 표기를 모름 ⑤ 서버가 `id`를 목록으로 보내면 예외 ⑥ 통과 기록 60개면 글 비교에 4.5초 ⑦ 작업 스레드가 Tk 변수(`var_lyrics`·`var_rename`·`var_country`·`var_query`)를 직접 읽음 ⑧ 예상 못 한 저장 오류를 "읽기 전용"으로 보고하고, 저장 직후 다시 읽기가 실패하면 요약 없이 작업이 멈춤 ⑨ 바빴던 곡을 다시 묻는 단계에는 연속 실패 차단이 없음 ⑩ 취소 뒤 상태 줄에 "취소됨"이 남지 않음
- 해결: `search_lyrics.record_text`가 가사를 꺼내는 유일한 길(정리·길이 확인), 판정과 결과가 모두 이것을 씀. 이름은 정규화한 뒤 그대로 비교(제목 0.9, 아티스트 0.8, 부분 일치는 짧은 쪽 3자 이상·길이 비 0.34 이상). 비교는 길이가 가까운 30개까지. 서버 값은 타입을 믿지 않음. 옵션 값은 버튼을 누른 순간 Tk 스레드에서 읽어 넘기고, 검색 국가는 일반 변수로 둠. 저장 오류는 읽기 전용·깨진 백업·그 밖(로그 + "저장하지 못했습니다")으로 나눔
- 재발 방지: `tests/test_lyrics_edge.py`(57개: 빈 글·자리표시 글·긴 글·정리, 이름 규칙, 4개 언어 버전 표기, 이상한 응답 7종, HTTP 오류, 길이 없음, 빈 이름, 취소). 화면은 가짜 서버·가짜 오류로 6가지(계속 바쁨, 한 번 바쁨, 저장 예외, 저장 뒤 읽기 실패, 찾는 중 취소, 저장 중 창 닫기)를 돌려 콜백 오류 0 확인. 규칙: **바깥에서 온 값은 타입부터 확인하고, 실패의 종류를 사용자에게 구분해 알린다. 작업 스레드는 Tk 객체를 만지지 않는다**

### A17. CLI `--auto`가 표지를 받지도 않고 "표지를 내려받지 못함"이라고 알림 (2026-10-12, 가사 CLI 시험 중 발견)

### A21. 새 버전 확인 중 창을 닫으면 프로세스가 죽을 수 있는 구조 (2026-10-14, v0.2.1에서 고침)
- 증상: 같은 구조로 만든 짝 도구(scan-pdf-split)에서, 응답을 기다리는 1.5~5.5초 사이에 창을 닫으면 `Tcl_AsyncDelete: async handler deleted by the wrong thread`로 종료됨(메인 통합 프로젝트 세션이 알려 옴). 이 앱에서는 실제 실행 흐름으로 7번 시험해 재현되지 않았음
- 원인: 작업 스레드가 `root.after(0, lambda: on_result(...))`를 부르려고 root와 App의 메서드를 붙잡고 있음. 창이 닫힌 뒤 그 스레드에서 마지막 참조가 풀리면 Tk 변수가 Tk 스레드가 아닌 곳에서 정리됨. 언제 정리되는지(참조 계수인지 순환 수집인지, 어느 스레드인지)에 따라 갈리므로 재현되지 않았다고 안전한 것이 아님
- 해결: 작업 스레드는 모듈 함수 `_work(box, fetcher, slug, version, skipped)`로 결과를 dict에 담기만 하고, Tk 스레드가 `root.after(100, poll)`로 가져가 on_result를 부름. 시간 제한(4초+6초)이 지나면 폴링을 그만둠. 알림 문구도 "새 버전이 나왔습니다: {latest} (현재 {current})"로 바꿈(버전 뒤 조사가 어색)
- 재발 방지: `test_worker_thread_gets_no_tk_object_or_callback`(스레드 함수가 아무것도 붙잡지 않고, 인자에 root·콜백이 없음 — 고치기 전 코드에서 실패), `test_tk_side_stops_polling_after_the_timeout`, `tests/test_update_close.py`(요청 중 창 닫기를 별도 프로세스로 3번, 모두 살아남아야 함). 규칙: **작업 스레드에는 Tk 객체도, Tk 객체를 붙잡은 콜백도 넘기지 않는다. 결과는 Tk 스레드가 가져간다**
